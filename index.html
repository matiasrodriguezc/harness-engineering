The concept

Agent = model + harness

The model pulls; the harness decides where that force goes. The course's idea is that when an agent fails, you check the harness first and the model only after. I put it to the test in eight projects, changing only the harness and measuring what happened. A harness has five plies:

  • InstructionsA short AGENTS.md that routes to the docs, with startup and wrap-up rules.
  • ToolsShell, files, tests and verification scripts, with least privilege.
  • EnvironmentAn init.sh that confirms the project builds and starts before any work.
  • StateFeature list, handoff and progress log for the next session.
  • VerificationTypes, tests and an end-to-end test in the real app.

Findings

The main one

With current models, the harness changes how the work gets done more than whether it gets finished.

In almost every project both versions delivered the task. The harness shifted the cost, the verification, the tests, the commits and what gets written down for the next session.

Verification · P03

The wrong kind of evidence produces false "done".

Two agents marked four features as done with the UI disconnected. They followed the rule of never marking without evidence, but the evidence was the build and service tests. Only a test in the real app catches it.

The course

The course's own solutions repeat a bug.

The preload imports a local file with Electron's sandbox on, and the UI is left without access to the app, even in the final project's solution that its own rubric grades 5/5. I turned it into an executable rule.

Specification · P06

A well-specified task did much of the work.

With fixed API names and "it has to work in the real app", all five variants passed the hidden 12-check suite, including the weak harness.

Roles · P05

An independent evaluator adds value; a planner, not always.

By the same judge, the evaluator that used the app raised the score from 3.9 to 4.5. The planner widened the work, cost more and ended at 4.0.

Loops and graphs · P07, P08

A loop is only as good as its stop condition.

The timer loop checked first without an agent and only woke one when something failed: it reverted two failures for US$0.23. Drawing the loop as a graph exposed four decisions nobody had written down.

Reading the numbers

Limitations

  • One run per condition: differences in time and cost are indicative, not statistical.
  • A single model, Claude Opus 5.5. With another, several conclusions may change.
  • Sessions ran in non-interactive mode, not by hand as the course suggests, so they could all be measured the same way.
  • I designed several protocols myself because the course does not define them; every adjustment is in its project's metrics.md.
